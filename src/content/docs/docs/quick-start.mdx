knomit is a distributed, decentralized knowledge distillation factory: a fabric
of many agents and many knowledge bases, in which what any one agent learns is
accumulated, distilled and put to use by all of them. This page gets one server
running with one knowledge base and one agent connected to it; the
[Overview](/docs/overview/) shows how the pieces scale from there.

## Install

The quickest way in is a signed release build — no toolchain, no compile step.

<CardGrid>
  <Card title="Download a release" icon="download">
    Grab the [desktop app or the server tarball](/download/). Releases ship for
    **macOS (Apple Silicon)** and **Linux (x86_64)**; a container image is
    published too (see [Deployment](/docs/deployment/)). The macOS app is
    notarized and keeps itself up to date. **Start here unless you need to
    modify knomit.**
  </Card>
  <Card title="Build from source" icon="seti:go">
    Everything below. Needed if you are changing knomit itself, or running on a
    platform the releases do not cover — **Windows is supported as a
    build-from-source target**, not a download.
  </Card>
</CardGrid>

A build produces four binaries:

| Binary | Role |
|--------|------|
| `knomit` | The server: REST API, MCP endpoint, embedded web UI, git endpoint. Also the admin CLI (`verify`, `fleet`, `identity`, `grants`, `oauth`). |
| `kb` | The bridge: a stdio-to-HTTP adapter that MCP clients launch, plus the `claude init` and `antigravity init` scaffolders and the editor hooks. |
| `knomit-okf` | Publishes a knowledge base as an [OKF](/docs/okf/) repository. |
| `knomit-desktop` | The tray app that runs the server in-process. Built by `make desktop`, not `make build`. |

The release server tarball contains `knomit`, `kb` and `knomit-okf`. See the
[CLI reference](/docs/cli-reference/) for every command and flag.

## Build from source

### Requirements

- **Go 1.26+** — the entire backend.
- **Node.js + npm** — builds the embedded React frontend.
- **Git CLI** — knomit shells out to `git`.
- **A C compiler and the SQLite development header.** The build is CGO-based,
  and the compiler needs `sqlite3.h` on its include path: Xcode Command Line
  Tools on macOS (`xcode-select --install`, which includes the SDK header),
  `build-essential` plus `libsqlite3-dev` on Debian and Ubuntu, or
  `mingw-w64-x86_64-sqlite3` under MSYS2 on Windows. Only the header is needed;
  nothing links a system SQLite.
- **Windows only:** Rust and cargo with the `x86_64-pc-windows-gnu` target
  (`rustup target add x86_64-pc-windows-gnu`), because `make setup` builds the
  tokenizer library from source there. The desktop app also needs the WebView2
  runtime, which Windows 11 includes.

<Aside type="note">
`make setup` and `make build` fetch the native libraries into
`dist/<goos>-<goarch>/lib/` by themselves: **ONNX Runtime** (embeddings), loaded
at run time, and the tokenizer library `libtokenizers.a`, linked statically at
build time. You do not install either by hand. The build writes the binaries to
`dist/<goos>-<goarch>/` and exposes `dist/knomit`, `dist/kb` and
`dist/knomit-okf` as symlinks on macOS and Linux and as copies on Windows.
</Aside>

### Build and run

<Steps>

1. Clone the repository and enter it.

   ```sh
   git clone https://github.com/knomit/knomit.git
   cd knomit
   ```

2. Download the native libraries (one-time).

   ```sh
   make setup
   ```

3. Build the web frontend and the Go binaries.

   ```sh
   make build
   ```

4. Start the server.

   ```sh
   make run
   ```

</Steps>

Open <strong>http://localhost:19278/</strong> for the web UI. A fresh install
starts with **no repositories** — the UI's "no repos" screen is the ordinary
first-run state, not an error.

<Aside type="tip" title="Prefer a native app?">
The [desktop app](/docs/desktop/) is a system-tray app that runs the server
in-process and lets MCP clients auto-discover it — no terminal needed to keep
knomit running. Most people should just [download it](/download/). To build it
here instead of `make run`, use `make desktop`: on macOS that produces
`dist/darwin-<arch>/Knomit.app` (`darwin-arm64` on Apple Silicon); on other platforms it produces the
`knomit-desktop` binary (plus `kb` and `knomit-okf`) in `dist/<platform>/`. On
Linux, run `make desktop-install` afterwards for the `.desktop` launcher and
icon.
</Aside>

## Create your first knowledge base

A repo is one knowledge base, and no repo is privileged: knomit starts with
none, and nothing falls back to a default name. Create the first one from the
gear icon in the web UI, which opens a [wizard](/docs/web-ui/#creating-a-repository),
or over the REST API.

The create call has six modes. Three are local and three involve a remote:

| Mode | What it does |
|------|--------------|
| `preset` | A new local repo with one of the built-in [ontologies](/docs/ontologies/). |
| `custom` | A new local repo with an ontology you supply as YAML. |
| `template` | A new local repo seeded from a [template](/docs/templates/) held by a repo that is already mounted. |
| `clone` | Joins a remote branch that is already a knowledge base. |
| `initialize` | Starts a knowledge base on a remote branch that is not one yet. |
| `subscribe` | Follows a remote knowledge base read-only. A subscription has no agent branch and refuses writes. |

The ontology is the set of topics a repo accepts and the rules every fact is
validated against, and it is chosen when the repo is created. It lives in the repo
as `.knomit/ontology.yaml`; changing it later means committing a new version of
that file through git. Choose by what the knowledge base will hold. The
`default` preset is a broad subject taxonomy (people, technology, science,
society, culture, business and more). The `code` preset is a set of topics for
knowledge about a codebase: invariants, architecture, conventions, decisions,
gotchas, incidents, principles and meta. The `fleet` preset holds the member records of a [fleet](/docs/fleet/).
For anything else, write a custom ontology or start from a template. If you point
knomit at a branch that is *already* a knowledge base, the question does not
come up at all: that repo's own ontology governs.

<Tabs>
  <TabItem label="Preset">

  ```sh
  curl -X POST http://localhost:19278/api/v1/repos \
    -H 'Content-Type: application/json' \
    -d '{"name":"work","mode":"preset","ontology_preset":"default"}'
  ```

  </TabItem>
  <TabItem label="Template">

  A template lives in a repo that is already mounted and supplies the new repo's
  ontology and starting files. Name the mounted repo and the template:

  ```sh
  curl -X POST http://localhost:19278/api/v1/repos \
    -H 'Content-Type: application/json' \
    -d '{"name":"ops","mode":"template","template":{"repo":"<mounted-repo>","name":"<template-name>"}}'
  ```

  The `kb` bridge has a shorthand for the same call:

  ```sh
  kb repo create ops --template <mounted-repo>/<template-name>
  ```

  </TabItem>
</Tabs>

A create runs as a background job: the call returns `202 Accepted` with a
`Location` header pointing at `/api/v1/repo-creates/{id}`, and the job survives a
closed browser tab. The web UI shows the repo as a pending row and can cancel it.

<Aside type="tip" title="Where repos can be created">
Repos are created, archived, restored and purged at runtime through the web UI
or the [REST API](/docs/api/), with no restart. `kb repo create --template` is
the only CLI route, and MCP tools cannot create repos at all. Archiving your
last repo is allowed; it stays restorable.
</Aside>

## Connect an agent over MCP

An MCP client reaches the server through `kb`, a stdio adapter it launches as a
subprocess. `kb` runs in one of three modes, chosen by its flags:

<Tabs>
  <TabItem label="Scoped to a repo (.mcp.json)">

  ```json
  {
    "mcpServers": {
      "knomit-repo-core": {
        "command": "kb",
        "args": ["--repo", "core"]
      }
    }
  }
  ```

  `kb` must be on the client's `PATH`; otherwise give `command` as the path to
  the binary, such as `dist/kb`. `kb` finds the repo's agent branch from the
  running server by itself, so you never look it up by hand.

  To read across several repos at once, use a [lens](/docs/lenses/) instead:
  `"args": ["--lens", "<lens-name>"]`. `--lens` and `--repo` are mutually
  exclusive, and a flag given with an empty value is an error.

  </TabItem>
  <TabItem label="Unscoped (the agent binds)">

  ```json
  {
    "mcpServers": {
      "knomit-repo-myproject": {
        "command": "kb",
        "args": []
      }
    }
  }
  ```

  (`kb claude init` names the entry after the directory.)

  With neither flag, `kb` connects to the unscoped endpoint `/api/v1/mcp`, where
  nothing is bound yet. The agent calls `knomit_repos` to see the repos and
  lenses the server offers, then `knomit_bind` with one name. `knomit_bind`
  returns an opaque `binding` handle, and the agent passes it as the `binding`
  argument on every later call. Binding is per call rather than per connection,
  so several independent jobs can share one `kb` process and each work in a
  different repo. See [MCP tools](/docs/mcp-tools/#the-endpoints).

  </TabItem>
  <TabItem label="Streamable HTTP">

  A client that speaks streamable HTTP can skip `kb`. Substitute the agent
  branch logged on startup (`/` becomes `:` in the URL path):

  ```json
  {
    "mcpServers": {
      "knomit": {
        "type": "streamable-http",
        "url": "http://localhost:19278/api/v1/repos/core/branches/agent:hostname-abc123/mcp"
      }
    }
  }
  ```

  A [lens](/docs/lenses/) has no branch segment: its URL is
  `http://localhost:19278/api/v1/lenses/<lens-name>/mcp`. The unscoped endpoint
  is `http://localhost:19278/api/v1/mcp`.

  </TabItem>
</Tabs>

### Which server `kb` talks to

`kb` talks to one server for everything it does. The first match wins:

1. the positional `server` argument (the proxy only; hooks take none),
2. the `KNOMIT_SERVER` environment variable,
3. the desktop app's lockfile (`server.json`),
4. `http://localhost:19278`.

The argument and the variable accept `http://host:port`, `https://host:port`,
`unix:///path/to/knomit.sock` and, on Windows, `npipe:////./pipe/<name>`. Each
server logs its own address at startup in exactly this spelling. The
[CLI reference](/docs/cli-reference/#kb--mcp-proxy-and-agent-integration)
has the details.

### Scaffold the integration

<Aside type="tip" title="Let kb write this for you">
`kb claude init` scaffolds the Claude Code integration in the current directory:
a `.mcp.json` entry, the editor hooks in `.claude/settings.json`, eleven
`/knomit-…` skills under `.claude/skills/`, and a versioned block in `CLAUDE.md`
(block v5). Run it with `--repo <name>` or `--lens <name>` to scope the entry, or
with neither for the unscoped form above. `.mcp.json`, `.claude/settings.json`
and `CLAUDE.md` are **merged** in place, so your own entries and formatting
survive a re-run. See [Claude Code](/docs/claude-code/).

`kb antigravity init` (alias `agy`) does the same for Antigravity; see
[Antigravity](/docs/antigravity/).

The tools are usable without any of it — their descriptions carry the guidance a
model needs to call them correctly. What the skills and the `CLAUDE.md` block add
is *when* to reach for them: recall before touching an unfamiliar area, record a
decision once it is made, re-verify a fact before relying on it.
</Aside>

## Write your first fact

With an agent connected, ask it to record something it has worked out. Under the
hood it calls `knomit_learn`, which writes a markdown fact and commits it. A
stored fact looks like this (frontmatter abbreviated):

```markdown
---
kind: epistemic
type: observation
confidence: 0.8
domain: [suppliers, logistics]
entities: [Acme Freight]
---
# Acme Freight's Rotterdam lane adds two days in Q4

Acme Freight's Rotterdam–Hamburg lane ran two days over quote on every Q4 shipment logged this year.
Plan Q4 orders with that margin.
```

That write is one atomic, signed git commit on your agent's branch. Browse it in
the web UI, or query it back with `knomit_query`. Facts can cite what they rest
on in `refs`; see [Concepts](/docs/concepts/) for the reference forms.
