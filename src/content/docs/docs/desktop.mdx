`knomit-desktop` is a native [Wails v3](https://v3.wails.io) application: a
system-tray icon plus a native webview window showing the same web UI. It is the
easiest way to keep a knomit server running on your machine — no terminal, no
manual `serve`.

What you see inside that window is the [web UI](/docs/web-ui/) — same code, same
surfaces, screenshots and all. This page covers what the desktop app adds around
it: how it runs the server, how it is installed, and how it updates.

It works differently from a bare `knomit serve`, and those differences matter for
wiring up MCP clients.

## How it differs from `knomit serve`

- **Runs the server in-process.** The app boots the full knomit server inside
  itself on a **loopback port** (it prefers `19278`, or `port` from
  `knomit.toml`, and picks a free port if that's taken) and serves the web UI
  from embedded assets. That port is a pure REST/MCP endpoint — the same one
  Claude Code and other MCP clients call.
- **Opens the same listeners, minus one.** Beside the loopback port it opens the
  local authenticated listener (a unix socket, or a named pipe on Windows), so a
  `kb` on the same machine is identified by the user id the OS reports. When
  `[tls].addr` is set and a certificate is installed, it also opens the mTLS
  listener for enrolled fleet peers; if that address is already held (usually by
  a `knomit serve` on the same data root), the desktop logs a warning and
  carries on without it rather than losing the UI. It never opens the OAuth
  listener, so the approval panel for OAuth requests does not exist in the
  desktop.
- **Publishes a discovery lockfile.** Once every listener that can fail is open,
  it writes `server.json` (`{pid, port, version}`, mode `0600`, written
  atomically) so `kb` can find the running server's port without being told. The
  file lives outside `KNOMIT_HOME`:
  - macOS: `~/Library/Application Support/knomit/server.json`
  - Linux: `$XDG_STATE_HOME/knomit/server.json` (falling back to
    `~/.local/state/knomit/server.json` when `XDG_STATE_HOME` is unset)
  - Windows: `%LOCALAPPDATA%\knomit\server.json`

  The same file stops a second launch: if the recorded process is alive, the new
  one prints "knomit-desktop is already running." and exits. The lockfile names
  exactly one server, so run one desktop per data root. To reach a second
  instance, give `kb` its address in `KNOMIT_SERVER`.
- **Lives in the system tray.** On every platform it runs as a tray app
  (`Knomit.app` on macOS). The tray menu has **Open Knomit** (shows the webview
  window), **Settings…**, **Check for Updates…** where self-update is live (below),
  and **Quit**. Closing the window hides it; the server keeps running.
- **Appears before it is ready.** Startup is tray-first: the icon shows up
  immediately with an **amber badge** while the server boots in the background,
  rather than leaving you with nothing on screen during a cold start.
- **Has its own Settings window.** Port, log level and format, start at login,
  and the mTLS listener address are native settings off the tray menu, with a
  button to restart the app and one to reveal the log file; a field that an
  environment variable overrides is disabled and says so. A **Fleet identity**
  section installs the certificate bundle that enrols this machine in a fleet,
  the same install `knomit identity install` performs, so a desktop without the
  CLI can join. It is reachable only from the Settings window.
- **Installs `kb` and `knomit-okf`.** On launch the app places the bundled `kb`
  (the MCP bridge) and `knomit-okf` into `$KNOMIT_HOME/bin` (default
  `~/.knomit/bin`), giving MCP clients a stable path to point at: symlinks on
  macOS, copies on Linux and Windows (an AppImage's contents vanish when it
  exits, and an ordinary Windows user cannot create symlinks). It removes the
  pre-rename `knomit-bridge` link.

<Aside type="tip" title="Why the lockfile matters">
Because the app may land on a non-default port, `kb` discovers the server through
`server.json` rather than assuming `19278`. Register `kb` in an MCP client with
no server argument and it will find the running desktop server automatically —
see [Claude Cowork](/docs/claude-cowork/) and
[Claude Code](/docs/claude-code/). The order `kb` follows is: its argument,
`KNOMIT_SERVER`, this lockfile, then `http://localhost:19278`.
</Aside>

### The first-launch screen

A first launch can take minutes: the app installs its bundled tools, downloads
the embedding model (about 600 MB) and starts the engine before the server
exists. The window does not sit on a blank splash for that time. The desktop
answers the window's own requests while the server is down: `/config.js` says the
server is booting, and a desktop-served `GET /boot/status` returns
`{ready, phase, api_base?, error?}`, which the window polls every second. The
phase is one of `starting`, `installing-tools`, `downloading-models`,
`starting-engine`, `starting-server`, `ready` or `failed`, and the boot screen
shows what it is waiting on. The window makes no API call until the status says
`ready`; it then adopts the API base the status carries and carries on without a
reload. A failed boot shows its error on the same screen.

### Logs

The desktop no longer has its own Logs window or a tray item for one. The server
log is in the main window, at **Manage → Logs**, streamed live from the in-process
server like any other API data; see [Observability](/docs/observability/). The
desktop still writes a log file (rotating, 10 MB by 3 backups, 14 days by
default unless `knomit.toml` says otherwise), which is the record to look at after
a crash or a failed start. Its path is in Settings.

## Install

[Download a release](/download/) — that is the intended path, and on macOS it is
also the one that gets you updates.

- **macOS** — the `.app` is signed with a Developer ID and **notarized**, with
  the ticket stapled into the bundle, so a first launch works offline and needs
  no `xattr`, no right-click-Open, and no trip through Privacy & Security. Drag
  it to Applications.
- **Linux** — a single AppImage. It needs **GTK 4 and WebKitGTK 6.0** on the
  host. `chmod +x` it and run it; on a host without FUSE, prefix the command
  with `APPIMAGE_EXTRACT_AND_RUN=1`.
- **Windows** — there is no release download. Build it from source, as below.

## Updates

**macOS builds update themselves.** The app polls a signed appcast every six
hours, with a first check shortly after launch, and posts a notification when a
newer version exists. It never opens a window to tell you, and a check that finds
nothing is silent. Nothing installs until you press **Install & Restart** on that
notification — deliberately, since an update may migrate your knowledge base and
**migrations do not reverse**. You can also check on demand from the tray menu.

Each artifact carries a detached `.ed25519` signature over its SHA-256 digest,
and the updater verifies it against a key pinned at build time, refusing
anything that does not match. A build with no pinned key (a local `make`) has no
updater at all, and no menu item for one.

**Linux and Windows do not self-update.** The AppImage is signed and published
like every other artifact, but the updater is switched off outside macOS: its
binary-swap step resolves paths inside the AppImage's temporary FUSE mount
rather than the AppImage file itself. Download a newer AppImage to upgrade.

## Build from source

Build the app with `make desktop`:

- **macOS** — produces `dist/darwin-arm64/Knomit.app`. Launch with
  `open dist/darwin-arm64/Knomit.app`.
- **Linux** — `make desktop` writes `dist/linux-<arch>/knomit-desktop` beside
  `kb` and `knomit-okf`. Run `make desktop-deps` once for the GTK 4 and WebKitGTK
  development packages (apt-based systems), and `make desktop-install` to copy the
  binary to `$XDG_BIN` (default `~/.local/bin`), an icon to the hicolor theme, and
  a `knomit-desktop.desktop` launcher to `$XDG_DATA/applications`.
- **Windows** — see below.

Wails cannot cross-compile, so each build is for the platform you run it on.
Logs go to stderr and a rotating file under the platform logs dir
(`~/Library/Logs/knomit` on macOS, `$XDG_STATE_HOME/knomit` — fallback
`~/.local/state/knomit` — on Linux, `%LOCALAPPDATA%\knomit` on Windows). See
the [CLI reference](/docs/cli-reference/#knomit-desktop--traydesktop-app) for the
full argument list.

## Windows

The server, the desktop app and `kb` are built, tested and run on Windows; only
the release download is missing. To build from source you need:

- the Go version named in `go.mod`, Node.js and npm, and the Git CLI;
- a C compiler (the build uses CGO) with the SQLite development header
  `sqlite3.h` on its include path. With MSYS2, install
  `mingw-w64-x86_64-sqlite3`. Only the header is needed; nothing links a system
  SQLite;
- Rust and `cargo`, with `rustup target add x86_64-pc-windows-gnu`, because
  `make setup` builds the tokenizers library from source on Windows;
- the WebView2 Evergreen runtime, which Windows 11 already has.

`make setup`, then `make desktop`, produces `dist\windows-<arch>\knomit-desktop.exe`
with `kb.exe` and `knomit-okf.exe`. A few things behave differently from the
other platforms:

- **No console.** `knomit-desktop.exe` is linked for the Windows GUI subsystem,
  so it opens no console window and closing the terminal you started it from
  cannot kill it. `knomit-desktop.exe --version` re-attaches to the launching
  console so it still prints there. `knomit.exe`, `kb.exe` and `knomit-okf.exe`
  remain ordinary console programs.
- **Data root.** `%LOCALAPPDATA%\knomit\home`, with `server.json` and the logs one
  level up in `%LOCALAPPDATA%\knomit`. See
  [Configuration](/docs/configuration/#knomit_home-and-the-data-layout).
- **Local listener.** A named pipe, `\\.\pipe\knomit-<hash of the data root>`,
  restricted to your user and checked by `kb`. A pipe that some other process
  owns is a failure, not something `kb` quietly falls back from to TCP.
- **`kb` log.** `%TEMP%\knomit-bridge.log` by default.

<Aside type="note">
Releases ship macOS (Apple Silicon) and Linux (x86-64) artifacts. Windows is
built and tested in CI, but it is not published, so treat a Windows install as a
from-source deployment.
</Aside>
