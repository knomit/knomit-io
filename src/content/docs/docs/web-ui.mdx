The server embeds a React single-page app at `/`. It reads a knowledge base —
browse facts, search, inspect provenance, time-travel through history — and it
operates the server around it: it creates and archives repos, shows the
experiments agents have open, lists the MCP client sessions the server has seen, and
streams the server's log. It browses either a single repo or a
[lens](/docs/lenses/): one write repo plus any number of read mounts, federated
into one virtual knowledge base.

The page has two halves. [Layout](#layout) is the one section that says where
things are on screen. Everything after it describes what the UI can do, without
tying it to a particular control.

## Layout

### Top bar

- A **context switcher** lists two groups, Repositories and Lenses. It appears when more
  than one repo exists, when any lens exists, or when you are already browsing a
  lens. A repo or lens whose store is unavailable is marked there.
- In a lens context the right zone shows a **lens chip** and a **mounts
  picker**: a count of the mounts being read (`n/N` when narrowed) that opens a
  checklist of the read mounts. The status footer names the write mount
  (`✎ <write repo>`).
- In a repo context the **branch chip** opens a picker listing the agent branch
  and the repo's experiments; choosing one enters it. Orphaned experiments are
  listed but disabled. Inside an experiment the chip shows a flask and the
  experiment's name, and an **experiment band** appears under the top bar (see
  [Experiments](#experiments)).
- A **gear icon** enters and leaves **Manage**. One control at one anchor: from
  browse it opens Manage, and from inside Manage it returns you to browsing.
  `Escape` leaves Manage too.

### Browse

- The **library** is on the left. It switches between four ways of looking:
  **Path** (the ontology tree), **Recent**, **Relevance** (while a search is
  running) and **Motif** (while a motif pivot is on).
- The search and filter field sits in the top bar while you are live; in history
  it gives way to the trail breadcrumb. A **filter bar** offers the filter chips
  Domain, Entity, Kind, Type, Origin, Motif and Path. In a lens the Motif
  vocabulary is every mount's motifs merged into one list.
- The **right panel** shows the folder overview or the open fact. The fact's
  header has three rows: type, origin, confidence and source count (plus the
  source mount in a lens); the path; then the connection counts and the fact's
  motifs on the left, with the version's date, the version chip and the retract
  control pinned right.
- The **status footer** shows the live/history indicator, the anchored commit,
  the running build version, and a count of repo creates in flight.
- In a lens context the library shows one ontology tree merged across every
  mount, and:

  | Surface | In a lens context |
  |---------|-------------------|
  | Mounts picker (top bar) | narrows the union to a subset of read mounts; selecting every mount collapses back to all mounts |
  | `repo:` filter | not a chip in either context; narrow a lens to some of its mounts with the mounts picker |
  | Fact view | shows a source-mount badge; editing is permitted only for write-repo facts |
  | Colours | each repo gets a deterministic colour, the same wherever it appears |

### Manage

Manage is a **mode, not a dialog** — it replaces the browse surface rather than
floating above it. Its pages run across the top as a tab strip; the entities you
own (repositories and lenses) run down a rail beside them. The strip appears
once at least one repo exists; with none, Manage is the create screen.

| Tab | Page |
|-----|------|
| **Knowledge** | The overview of what needs doing and what is wired to what, plus a page per repo and per lens, and the archive. The rail lists repos and lenses |
| **Fleet** | This instance's [fleet](/docs/fleet/) membership |
| **Sessions** | The MCP client sessions and whether each is live, idle or dead. Its badge counts live sessions, with a `+` when the list is truncated |
| **Logs** | The server's log, live. Absent on a read-only server |
| **Authorizations** | OAuth requests waiting for an operator. Present only where the server runs an OAuth issuer, and absent on a read-only server. Its badge counts pending requests |

The rail is shown beside pages about entities and dropped on the server pages
(Fleet, Sessions, Logs, Authorizations), which take the full width. A repo's
own page is a column of blocks, in order: Description, License, Agent branch,
Experiments, Pushed branches (absent on a subscription), Remote, Mounted in,
Agent access, Index and a Danger zone for rename and archive. A repo that is still being created shows
the same page, gated until the create finishes.

### Keyboard

Four global keys, ignored while a text field has focus:

| Key | Effect |
|-----|--------|
| `/` | Focus the search/filter input |
| `Escape` | While time-travelling, return to now; otherwise clear the active filters |
| `Backspace` / `Delete` | Navigate back |
| `h` | Return to HEAD, leaving time-travel |

`⌘[` and `Alt+←` also navigate back, and work even with a field focused. While
anchored live, the library list also takes `j` and `k` or the arrow keys to move
the selection and `Enter` to open it.

## Browsing and searching

- **Library & search** — browse the ontology tree and run full-text + vector
  search across facts. Filter by domain, entity, kind, type, origin, path and
  **motif**, singly or together; the same filters narrow the folder overview.
- **Motifs** — a motif is a general regularity a fact is an instance of, such as
  a mechanism or a failure shape, independent of the fact's subject. A fact
  shows its motifs; opening one explains it and offers a **pivot** to every fact
  in the knowledge base that shares it, whatever its subject. The summary also
  lists the repo's motif vocabulary.
- **Inspect a fact** — read its frontmatter, body, and provenance: the signed
  commit, the refs it anchors to, and how its confidence evolved. **Connection
  counts** in both directions (`↙` incoming, `↗` outgoing) each open a panel
  listing those refs. A count of zero renders as plain text rather than a
  button, so the layout doesn't shift between a connected fact and an isolated
  one.
- **Read its references honestly** — the server classifies every ref, and the UI
  renders each class differently: a resolvable fact is a clickable hop, a
  **broken** one is flagged rather than linked, and refs into another repo,
  into source code, or out to a URL are labelled as such. Whether a ref resolves
  is judged at the commit you are *viewing*, so a hop is never offered into a
  version where the target did not yet exist.
- **See when this version was written** — beside the version chip, every fact
  carries the commit date of *the version you are looking at*, not of the fact
  as a whole. It reads as a relative time when you are live, and as an absolute
  date, in amber, when you are in history — so a version from two years ago
  cannot be mistaken for the current one. It works the same for repo and lens
  facts.
- **Ontology browser** — navigate topics and categories and see inheritance.
- **Folder overview** — every folder, including the root, opens on a dashboard:
  headline counts, **facets** for the domains, entities and types in scope, and
  **highlights**, a top-ten of the facts the rest were built on.
- **Task progress** — synthesis and index tasks stream their progress live over
  server-sent events.

A panel that crashes renders a contained inline fallback; the rest of the app
stays usable.

### How highlights are ranked

Highlights answer "what is load-bearing here", so they rank by **impact**: the
number of distinct facts a fact was derived from. Observations and references
are excluded — they are the substrate the distilled layer is built *from*, and
including them would bury it — unless a folder holds nothing else, in which case
it gets its own top-ten rather than an empty panel.

Impact is deliberately **global**: a fact reports the same number from the repo
root as from its own folder, which is what lets you verify it by opening that
fact's connections. You can switch the ranking to confidence or recency; the
server picks the default per repo, falling back to confidence where the corpus
has no distilled layer for impact to separate.

## Time travel

View the knowledge graph as of any past commit; refs resolve to the versions that
existed at that point in time. Opening a fact's history lists its versions as a
timeline you can pick from, along with the other facts changed in the same
commit. Typing `at:<sha>` in the search field jumps to a commit, and
`vs:<from>..<to>` (short SHAs or `HEAD`) opens a **diff view** comparing the open
fact across two commits; in a lens, open a fact first. While you
are anchored in history the UI is read-only and says so, and one key returns you
to now.

## Experiments

An [experiment](/docs/experiments/) is a private `exp/<name>` branch that agents
open through the `knomit_experiment` tool and later commit or roll back as a
unit. The UI lets a person see and settle them:

- **A table of the repo's experiments**: name, description, last commit and when
  it expires. Every row can be rolled back; a row you are not in can be opened, and the experiment you are in can be committed. There is no
  control to create or sync an experiment; agents open them. The expiry line
  reports the server's `[experiments].expiry_days` policy and is not a control.
- **The experiment band**, shown while the window is inside an experiment: what
  it forked from, how many facts changed since the fork, when it lapses, and
  Commit and Roll back. The changed count comes from the same filter as the
  **since fork** toggle, which narrows the library to the facts the experiment
  touched.
- **A conflict dialog** when a commit is refused because both sides changed the
  same facts: it lists the conflicting paths, says nothing was changed, and points to resolving
  them through `knomit_experiment`; the only action it offers is rolling the
  experiment back.

A subscription has no agent branch to fork from and cannot hold an experiment.

## Pushed branches

When other instances push their agent branches to this host (see
[Fleet](/docs/fleet/) and [Sync, consensus & conflicts](/docs/sync-and-consensus/)),
a repo lists them with the number of commits each would bring. A person with the
`operator` permission can **merge** one into the repo's agent branch; nothing
merges on its own here. The merge is pinned to the exact commit the list shows,
so a push that lands while the confirmation is open is refused rather than
merged unseen. If the same facts changed on both sides, a conflict window shows
both versions of each fact first, then lets the operator keep the host's version
or take the peer's for the whole set. A subscription has no such list, since no
peer can push to one.

## Creating a repository

Creating a repo is a **guided wizard**, not a form with mode tabs. You are never
asked to classify your remote before you have the information to do it — the
wizard probes, and derives the rest from the answer. It produces one of six
modes: `preset`, `custom`, `template`, `clone`, `initialize` and `subscribe`
(see the [Quick start](/docs/quick-start/#create-your-first-knowledge-base)).

| Step | What it asks | When it appears |
|---|---|---|
| Source | Local-only (with the repo name) or a remote URL | always |
| Access | Credentials, plus the repo name — prefilled from the URL, since `git@host:org/arxiv-kb.git` is going to be called `arxiv-kb`. A `knomit+https` URL uses certificate authentication | remote |
| Branch | Which branch to build the knowledge base on. If the branch is already a knowledge base, join it or **subscribe** (read-only, pull-only) | remote with branches |
| Ontology | A preset, custom YAML, or a [template](/docs/templates/) from any mounted repo | local, or a remote branch that is not already a KB |
| Review | Confirm, then watch progress | when the shape is established |

The step list is **derived**, not stored, so a step is never "skipped" — it is
simply not part of your case. Joining a branch that already has an ontology
never asks you to pick one, because that ontology governs.

<Aside type="note" title="A check that did not complete never guesses">
The branch question — *does this branch already carry `.knomit/ontology.yaml`?* —
has three answers: yes, no, and could not tell. Guessing "yes" would discard the
ontology you chose; guessing "no" would write one over a knowledge base that
already had its own.

So when the check cannot be established, the step list ends at Branch and the
action reads Try again. Ontology and Review are not shown, because the wizard
cannot tell yet whether the branch is already a knowledge base.
</Aside>

The Branch step is separate from the initial probe because the answer is
**per-branch** — a repository can carry the ontology on `main` and not on
`develop` — and the branch is not known when the origin probe runs. A remote
with no branches at all is a dead end rather than a mode, and the Access step
says so: create a `main` first, one commit is enough.

The Ontology step offers the `default` and `code`
[presets](/docs/ontologies/#the-built-in-presets) (`fleet` is not offered there), a YAML editor with live validation, syntax highlighting and completion, or a
template. Every diagnostic is reported with its line position, and all of them at
once rather than only the first. An uploaded file is validated the same way before
it is accepted.

### A create runs in the background

Submitting the wizard starts a job on the server, which survives a closed tab. It
reports progress step by step — validating, reading or subscribing to the
remote (an indeterminate bar showing the remote's own progress lines),
registering and indexing — and counts as done only once
the repo is indexed. The new repo appears as a pending row you can open to watch,
and the UI enters the repo as soon as it exists. A running create can be
**cancelled**, which removes everything it made and leaves no archive entry. A
finished job is kept for an hour and can be dismissed. A create is refused up
front when the name is taken, when the origin is already in use by another active
repo, or when the remote is a knowledge base this server already holds a copy of;
the last check is made against the remote's advertised identity before any data
is transferred.

## Archiving and restoring

A repo can be archived, restored from the archive, or purged for good. A repo
whose storage is missing, cannot be opened, or conflicts with another copy can be
archived without being opened, with an optional note of up to 500 bytes explaining
why. Each archived entry shows its **reason** — whether a person or the system
archived it, and the note — and a system archive happens when a cancelled create
or a fleet removal could not purge its data, or when a repo's ontology is a
symlink. Restoring takes an optional new name and is refused when the name or
origin is already in use, when another active repo holds the same knowledge
base, or when a lens holds the name. An active repo whose ontology is missing, empty or
unparsable stays readable but refuses writes, and the UI says why.

## Index state

Search runs over an index that is built in the background, so a repo can be
readable before its index is complete. A repo whose index is being built carries
a progress chip (done over total), and one whose index failed or was cancelled
carries an error chip with the reason. Chips appear wherever the repo is listed
and vanish when the index is ready. Changes are pushed to the UI, so no refresh
is needed. A person can **rebuild** the index. Operations that need the index idle, such
as connecting or disconnecting an origin, are refused while it builds; the
refusal names the reason and offers **Cancel indexing**.

## Renaming and licensing

- **Rename a repository.** Gated on typing the current name. The rename re-keys
  the registry in place rather than closing the store, so SSE subscribers and
  the search index survive it. Repos and lenses share one namespace, so a name
  held by either is refused.
- **Rename a lens.** A lens is keyed by an internal `uid`, so its name is
  display-only and free to change. In-flight MCP cursors are pinned to that uid
  rather than the name, so a rename cannot orphan a paging session.
- **Create or edit the repository `LICENSE`.** A missing one can be created and
  an existing one edited. The read view stays preformatted rather than rendered
  as markdown, which would reflow away the line breaks a licence depends on. An
  existing `LICENSE` over 64 KiB is shown as present but not displayed, and the
  server refuses to replace it, since it would overwrite a file no one could
  read first.

## Connecting a remote

A local repo can be connected to a remote, and a connected one repaired, replaced
or disconnected, through a stepped flow: connect (with credentials or, for a
`knomit+https` URL, a certificate), review what would change, then sync. See
[Remote sync](/docs/remote-sync/).

## Browsing a lens

The **browse context** — a repo or a lens — is the single source of truth for
what you are looking at. In a lens context the active repo and branch stay
pointed at the lens's write mount, so write routing never breaks. The context is
persisted and restored across reloads; a lens deleted since the last visit falls
back to a repo context rather than erroring.

Creating a lens takes a name, an optional description, one write repo — which the
server also mounts for reading — and any number of read mounts, each with a
branch chosen from the branches that exist. Lens management also has a detail
view per lens.

## Sessions

The Sessions page lists every MCP client session the server has seen, one row
per session: the client, its parent application, host and working directory, the
repos and lenses it is bound to, when it was last seen, and how many requests it
made. A session's bindings are grouped by target, with the per-handle list
expandable and any experiment it works in shown on the target. A state dot says
whether the session is live, idle or dead.

MCP clients hold no open connection, so presence is derived from traffic: a
session is live within a tenth of `session.client_dead_after` of its last
request, dead after `client_dead_after` (one hour by default), hidden from the
default view after `client_hidden_after` (three hours) and purged after
`client_retention` (168 hours). A **Show hidden** toggle, remembered in the
browser, brings the hidden rows back, and a footer states the policy. The list
refreshes on a 30-second poll and is pushed over server-sent events when a
session starts, ends or is touched. What a client says about itself (bridge,
branch) is self-reported and unverified. On a read-only server the list is
redacted.

## Logs

The Logs page streams the server's own log: the last 2000 lines are replayed
oldest first, then new lines follow live. It filters by level ("and above") and
by text. It is unavailable on a read-only server, since the log is not part of a
public demo.

## Fleet

The Fleet page shows this instance's [fleet](/docs/fleet/) membership: whether it
is standalone, registering, registered or unregistering, the state of its own
member record, the last error the server recorded, and the fleet's members.
Registering takes a fleet repository URL and credentials; an action the current
state forbids is disabled with the reason.

## Authorizations

When the server runs an OAuth issuer, clients such as `kb login` park an
authorization request on it. The Authorizations page lists those pending requests
and lets an operator **approve** one, naming the subject the token acts as and its
permission ceiling, or **deny** it, instead of using `knomit oauth` in a
terminal. See [Authentication & permissions](/docs/auth/).

## Starting up

Until the first repo and branch are known, a boot screen shows a progress bar
(indeterminate during the desktop's server phase) and a label for what it is waiting on (connecting, the server, the repo, the
branch), an elapsed counter after two seconds, and attempt feedback on retries.
On the desktop app it continues the splash shown during the first boot.

## Read-only mode

A server started read-only (`KNOMIT_READ_ONLY`) turns every write control off
with the reason in its tooltip, withholds the Logs and Authorizations pages, and
redacts the Sessions list. A subscription and a time-travel excursion are
read-only in the same way, each with its own explanation. See
[Deployment](/docs/deployment/).

<Aside type="tip" title="Run it as a native app">
The same UI ships as a system-tray [desktop app](/docs/desktop/)
(`knomit-desktop`) that runs the server in-process and lets MCP clients
auto-discover it — the easiest way to keep knomit running on your machine.
</Aside>
